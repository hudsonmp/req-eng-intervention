# Golden Requirements Document: Restaurant Reservation System

## Assessment Ground Truth — Viewpoint Interaction Analysis

---

## Viewpoint 1: Diner

### Within-Viewpoint Interactions

**D1.** When a diner selects a time slot, the system shall only display slots that the owner has marked as available.

**D2.** When a diner selects a party size, the system shall only display sizes that the owner has enabled.

**D3.** When a diner confirms a reservation, the system shall require the diner to provide: name, phone number or email, and party size.

**D4.** When a diner confirms a reservation, the system shall display a confirmation with: reservation time, party size, and a unique confirmation code.

**D5.** When a diner attempts to book a slot that has reached capacity during their session, the system shall reject the booking and prompt the diner to select an alternative slot.

**D6.** When a diner has an existing reservation, the system shall allow them to view, modify, or cancel using their confirmation code.

**D7.** When a diner cancels a reservation, the system shall release the slot and make it available for other diners.

**D8.** When a diner modifies party size on an existing reservation, the system shall verify the new size is still allowed by the owner before confirming.

---

## Viewpoint 2: Restaurant Owner

### Within-Viewpoint Interactions

**R1.** When the owner toggles a time slot off, the system shall immediately remove that slot from the diner's available options.

**R2.** When the owner toggles a time slot on, the system shall immediately add that slot to the diner's available options.

**R3.** When the owner disables a party size, the system shall prevent diners from selecting that size for new reservations.

**R4.** When the owner enables a party size, the system shall allow diners to select that size for new reservations.

**R5.** When a reservation is made, the system shall display to the owner: diner name, contact information, party size, time slot, and confirmation code.

**R6.** When the owner views current settings, the system shall display: count of enabled time slots, count of enabled party sizes, and total current reservations.

**R7.** When the owner views reservations, the system shall list all active reservations sorted by time slot.

**R8.** When the owner needs to cancel a reservation (e.g., emergency closure), the system shall remove the reservation and flag that the diner needs to be notified.

**R9.** When the owner sets capacity per time slot, the system shall track reservation count against that capacity.

---

## Cross-Viewpoint Interactions

### Diner ↔ Owner

**DR1.** When the owner disables a time slot that a diner is currently viewing, the system shall prevent the diner from confirming a reservation for that slot.

**DR2.** When a diner completes a reservation, the system shall immediately increment the owner's reservation count and display the new reservation in the owner's view.

**DR3.** When a diner cancels a reservation, the system shall immediately decrement the owner's reservation count and remove the reservation from the owner's view.

**DR4.** When the owner disables a party size, existing reservations with that party size shall remain valid, but new reservations with that size shall be blocked.

**DR5.** When a time slot reaches the owner-defined capacity, the system shall display that slot as unavailable to diners while remaining visible (but full) to the owner.

**DR6.** When the owner modifies available slots or party sizes, the system shall reflect changes to diners within the same session without requiring page refresh.

**DR7.** When a diner provides contact information, only the owner (not other diners) shall have access to view that information.

---

## Data Integrity Requirements

**I1.** The system shall persist all reservation data such that reservations survive system restart.

**I2.** The system shall prevent double-booking of the same slot beyond capacity through atomic reservation operations.

**I3.** The system shall generate unique, non-sequential confirmation codes that cannot be guessed.

**I4.** The system shall associate each reservation with exactly one diner identity and one time slot.

**I5.** The system shall maintain an audit trail of reservation creation, modification, and cancellation timestamps.
